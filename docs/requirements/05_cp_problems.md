## 0. 結論（先に）

1. **新カテゴリ `CP`（競技プログラミング形式）を作る。ALG の拡張にはしない。** ALG は LRU・Trie・LFU のような「データ構造設計を語る面接問題」で、判定も unit 型が混ざる。CP は「標準入出力の完結プログラム＋厳密な制約＋TLE を誘う隠しテスト＋6 言語すべて」という別の型で、時間枠も 30/45 分が主になる。UI で「本番と同じ型だけ練習する」ための絞り込みにもなる。
2. **合計 500 問は維持し、CP を 150 問（30%）にして最大カテゴリにする。** 減らす先は FE 110→75、ALG 90→45（CP 的な種 30 件を CP へ移す）、ほか各 5〜15 問。種（seed）は題名だけなので、削っても失うものは無い。これは 04 §2.1 方針 1（「実装型が主、アルゴリズム型は従」）の変更なので、04 の改訂とセットで行う（§2.3）。
3. **難易度対応**: paiza C = L1（15/20 分）、paiza B = L2（30 分）、ABC-C = L3（30 分）、paiza A = L3（45 分）、paiza S / ABC-D 以上 = L4（45 分）。実行時間制限は全問 2 秒（runner の係数で Python/PHP ×3、TS ×2、判定はさらに ×1.5 の余裕）。
4. **第 1 バッチは 40 問**（L1×10 / L2×15 / L3×15、§5）。4 人の作成担当が衝突しないよう、id を 10 問ずつの連番（cp-0001〜0010 / 0011〜0020 / 0021〜0030 / 0031〜0040）に分け、各範囲に難易度と技法を混ぜた（§6）。
5. **作成を始める前に必須の修正が 2 つある**:
   (a) **セッション作成時に、選んだ言語と関係ない starter まで全部配っている**（`apps/web/src/lib/capture/server/sessions-api.ts:48`）。Run の entry は `files[0]`（`InterviewScreen.tsx:469`）。runner の `pickEntry` で実測すると、alg-0001 を C/Rust/Go/PHP で始めたときの entry は `main.py` になる（gcc などに Python のソースを渡すので CE になる）。6 言語の starter を持つ CP 問題では、Python で始めても `main.c` が実行される。
   (b) **selftest が時間制限を見ていない**（`scripts/selftest.ts:160` のタイムアウトは最低 15 秒で、言語係数も掛けない）。このままでは「参照解が Python で 12 秒かかっても PASS」になり、TLE トラップの有効性も検証できない。
6. **オリジナリティ**: paiza は問題・提出コード・ヒントの公開を禁じ、受験後に他者と問題を相談することも禁止行為としている（確認済）。実際に受けた問題を思い出して再現することはしない（ユーザーに思い出させることもしない）。作るのは「定番技法 × 新しい題材 × 独自のひねり」だけで、作成中に paiza/AtCoder の問題ページは見ない（§3）。
7. **品質の担保は機械検証が中心**: gen.py（決定的）が期待値を計算する。300 件以上のランダム小ケースで全探索解と突合し、6 言語の参照解すべてが隠しテストを通ることを確認する。さらに素朴解が最大ケースで TLE することを確認する。CP は 04 §4.1 が心配する「LLM 生成で質が落ちる」問題を機械的に抑えやすい型で、増やすならここが一番安全。
8. **リポジトリ容量**: 既存の ALG 7 問だけで約 25MB（1 問平均 3.6MB、最大は alg-0007 の 7.9MB）。第 1 バッチは 1 問 6MB 以下、合計 100MB 以下の上限で全ファイルを commit する。150 問規模（第 2 バッチ以降）では、大きいケースだけ gen で再生成して git 管理外にする方式へ移る（§4.3）。
9. **試験モード（無言）を推奨**。既存の録画なし（`PreflightScreen.tsx:271` の `norec`）と silent 面接官を 1 つのプリセットにまとめるだけなら小さい変更で済む。ただし、評価軸の切替と提出 1 回制限は範囲外とする（§1.5）。

### 1.2 典型トピック・規模・形式

| 層 | よく出る技法 | 入力規模 | 失点の主因 |
|---|---|---|---|
| paiza C | 条件分岐、ループ、文字列の切り出しと置換、2 次元配列、集計と並べ替え、時刻・単位の換算 | N ≤ 10^3（計算量はほぼ問われない） | 境界（以上/より大きい）、出力形式、行に空白を含む入力、丸め |

| ABC-C / paiza A | ソート＋貪欲、累積和・尺取り、二分探索（値・答え）、bit 全探索、順列全探索、BFS/DFS、簡単な DP、map/set による数え上げ、組合せ mod、上位として Union-Find・Dijkstra・トポロジカルソート | N ≤ 2×10^5 | O(N²) の TLE、int32 の溢れ、再帰の深さ、Python の入出力速度 |

形式: 入力は標準入力。1 行目に N（や H W）、続く行に配列（空白区切り、または paiza に多い 1 行 1 値）、最後に Q 行のクエリ。出力は最後に改行を付ける。paiza の問題文は「問題文 / 入力される値 / 期待する出力 / 条件 / 入力例 / 出力例」の順、AtCoder は「問題文 / 制約 / 入力 / 出力 / 入出力例」の順（要確認）。LCI では §4.2 の書式に揃える。

### 1.3 面接（talk-aloud）との違い

- **本番は 1 人で、無言で、時間を測られる。** 評価は隠しテストの通過だけで、説明は採点されない。質問ができないので、曖昧な点は制約と入出力例から自分で確定させる必要がある。
- **提出は 1 回きり（paiza）か、WA のたびにペナルティ（AtCoder）。** そのため「提出前に自分で入力を作って確かめる習慣」がそのまま点数になる。
- **paiza は部分点、AtCoder は全ケース AC で得点（要確認）。** paiza では素朴解でも小さいケースの分は点が取れるので、「まず素朴解を出してから改善する」判断も練習する価値がある。

### 1.4 それでも「説明」を鍛える意味と方法

talk-aloud は、無言の本番で頭の中でやるべき手順を声に出して確認する訓練として使える。CP の talking_points は次の 5 枠に固定し、各問題で中身を具体化する（G5 が要求する固有の用語を必ず入れる）。

1. **制約から計算量の上限を宣言する**: 「N=2×10^5 なので O(N log N) まで。C なら 1 秒に 10^8 回、Python なら 10^7 回が目安」。
2. **素朴解を示して、なぜ駄目かを言う**: 「全ペアで O(N²) = 2×10^10 回」。
3. **改善の鍵になる観察**（問題固有。例: 「和が M の倍数 ⇔ 余りが r と M−r」）。
4. **エッジケースを提出前に列挙する**: N=1、全部同じ値、該当なし、境界の等号、64bit の溢れ、到達不能。
5. **入出力と検証**: まとめて読む・まとめて出す。サンプル以外に自作の入力を 1 つ以上試す。

評価軸との対応（`packages/core/src/evaluation.ts:22-31`）: R1 要件確認 ≒ 制約と入出力形式の読み取り、R2 方針宣言 ≒ 計算量の見積もり、R3 トレードオフ ≒ 素朴解と改善の比較、R4 実装正確性 ≒ AC、R5 テスト意識 ≒ 自作ケース、R6 時間配分。03 の FR-E-16「アルゴリズム重視ペルソナ」を CP に既定で割り当てる。

### 1.5 試験モード（無言）— 推奨のみ

- **推奨する。** 本番と同じ「無言・時間制限・隠しテストは最後に 1 回」の状態で AC 率と所要時間を測る回を設ける。同じ問題を、別の日に talk-aloud で解き直して説明を練習する、という往復が効く。
- 小さく作れる部分: S2 の「試験モード」を 1 チェックにまとめる。中身は既存の `norec=1`（`PreflightScreen.tsx:271`）＋ `mode=silent` ＋ followup 無効。
- 範囲外: Submit を 1 回に制限すること、レビューで R4/R5/R6 だけを出すこと、paiza 換算スコア（通過ケース数 ÷ 全ケース数 ×100）の表示。どれも小さいが、評価側の仕様変更になる。
- 問題ファイルは両モードで共通にする（モードごとに問題を分けない）。

## 3. オリジナリティとライセンス

- **paiza**: 規約は問題・提出コード・ヒントの掲載を禁じている。受験後に他者と問題を相談することも禁止行為で、生成 AI の利用も同様（確認済）。したがって **「受けた問題を思い出して LCI で再現する」ことは、ユーザー自身の規約違反になりうる。Claude に思い出した内容を説明させることも同じ扱いになる。** この運用は採らないこと、ユーザーにも求めないことを明文化する。
- **AtCoder**: 問題文とテストデータの権利は AtCoder 側にある。二次利用の条件は（要確認）。過去コンテストのテストケースは公開されているが、**取り込まない**。
- **守るべき線**: 技法（累積和、BFS、二分探索…）そのものは誰のものでもない。避けるべきは **「特定の既存問題と、題材・ひねり・制約・入出力のまとまりが対応してしまうこと」**。作成側の手順は次のとおり。
  1. 作成中（WP の作業中）は paiza・AtCoder・LeetCode の問題ページを開かない（WebFetch/WebSearch もしない）。
  2. 題材は §5 のものを使う（倉庫、図書館、駐車場、送電網…）。高橋君/青木君や paiza のキャラクターなど、既存コンテストの登場人物・世界観は使わない。
  3. 作者が「これは ○○ の問題だ」と気づいたら、ひねりを 1 つ変える（何を問うか・制約・出力のどれか）。その一般名を `review.known_issues` に「類題の可能性: 〜」と残す。例: 最初に構想した「スイッチと電球の bit 全探索」は ABC128-C に近すぎたので、献立の最安被覆（cp-0013）に変えた。
  4. `source.origin` は「LCI オリジナル（技法: X / 題材: Y）」、`source.license: internal`。
  5. テストデータは自前の gen.py だけで作り、外部のデータは使わない。
- レビュー役のエージェント（別セッション）は、「既知の問題との対応」を G6 相当の観点として 1 問ずつ判定する。

## 4. 1 問あたりの品質基準

### 4.1 ディレクトリ構成

```
problems/CP/cp-0001-receipt-coupon/
  problem.md                 # frontmatter + 問題文 / 制約 / 面接官メモ / 振り返り用解説
  tests.json                 # kind: stdio。sample 2〜3 件 + hidden 10〜20 件
  tests/01.in 01.out …       # 01〜03 = sample（問題文の入出力例と完全一致）、11〜 = hidden
  gen/gen.py                 # 決定的な生成 + 期待値の計算 + brute との突合（--check で差分検査）
  gen/brute.py               # 小さい入力用の全探索（gen.py から import してよい）
  gen/naive.py               # TLE させたい素朴解（計算量の罠がある問題のみ。C で通りうるなら naive.c も）
  starter/{c,rust,python,go,typescript,php}/main.*
  solutions/{c,rust,python,go,typescript,php}/main.*
```

- ALG の既存問題は `tests/gen.py` に置いているが、移動しない。CP では、生成と判定のコードを `gen/` に分けて `tests/` をデータだけにする（サイズ検査を単純にするため）。
- **期待出力（.out）は commit する。** gen.py の計算方法が変わったときに、diff で気づけるようにするため。

### 4.2 問題文の書式（G3: 問題文は 600 字以内、`gates.ts:37`）

- `## 問題文`: 題材と課題を 600 字以内で書く（alg-0001 は入出力例込みで 297 字）。
- `## 制約`: 「入力」「出力」「制約（箇条書き、`入力はすべて整数` を含む）」「入力例 1〜3 / 出力例 1〜3」「制限時間 2 秒（Python/PHP ×3、TypeScript ×2）」「TypeScript は strip-types」。alg-0005 と同じ配置。
- 入力形式は混ぜる（空白区切り / 1 行 1 値 / 空白を含む行 / グリッド）。L1/L2 の一部は、空白を含む行を読ませること自体を罠にする。
- 比較モード: 整数・語の出力は `token`。空白に意味がある出力（cp-0004 / 0008 / 0031）は `exact`。小数は `float`（cp-0023、絶対/相対誤差 1e-6）。

### 4.3 テスト設計とサイズ予算

ケース構成（hidden は 10 件以上。paiza の「10 個以上」に合わせる）:

| 種類 | 件数 | 命名 | 中身 |
|---|---|---|---|
| sample | 2〜3 | `sample-*` | 問題文の例と同一。1 つは「該当なし」などの特殊な結果にする |
| 最小・特殊 | 2〜4 | `hidden-min-*` / `hidden-edge-*` | N=1、全部同じ値、該当なし、境界の等号 |
| 罠ごとに 1 件以上 | 1〜4 | `hidden-trap-<名前>` | §5 の「罠」列の各項目を、それだけで落ちるように作る |
| ランダム小 | 3〜5 | `hidden-rand-*` | brute と突合済み |
| ランダム中 | 1〜2 | `hidden-mid-*` | |
| 最大 | 2〜4 | `hidden-max-*` | 素朴解に最悪となる形（鎖状、蛇行、全部同じ値など） |

- **TLE の罠**: 計算量の罠がある問題（§5 で「TLE」と書いたもの）は、`gen/naive.py` が少なくとも 1 件の `hidden-max-*` で制限（2 秒×3×1.5 = 9 秒）を超えること。C の O(N²) は N=2×10^5 で 9.4 秒（実測、`-O2`）で落ちる。一方 N=10^5 では約 2.3 秒と見積もられ、判定の閾値 3 秒を下回って通ってしまう。**C の素朴解まで落としたい問題は N ≥ 2×10^5 にする。** 出力サイズとの兼ね合いで N を下げた問題（cp-0005 など）は、「C の素朴解は通りうる」と `known_issues` に書く。
- **参照解の速度**: 全ケースで各言語の制限の 50% 以下（C/Rust/Go ≤ 1.0 秒、TS ≤ 2.0 秒、Python/PHP ≤ 3.0 秒、このコンテナで計測）。Mac の Docker 上での揺れと、runner の `python3 -u`（下記）に備えた余裕。
- **Python の出力**: runner は `python3 -I -u` で実行する（`packages/runner/src/languages.ts:95`）。selftest は `-u` を付けない（`selftest.ts:33`）。2×10^5 行を 1 行ずつ print すると、パイプ経由で 0.07 秒 → 0.65 秒（実測）と 10 倍遅くなる。参照解はまとめて出力する。runner 側の扱いは §8 T7 で直す。
- **サイズ上限（第 1 バッチ）**: .in は 1 ファイル 2.5MB 以下、.out は 1 ファイル 1MB 以下、`tests/` は 1 問 6MB 以下、L1 は 1 問 200KB 以下、40 問の合計 100MB 以下。出力が 512KB を超えうる問題は `limits.outputKb` を期待出力の 2 倍以上にする（既定は 1MiB、02 FR-X-01-3）。
- **第 2 バッチ以降**: `hidden-max-*` の .in だけを git 管理外にする（`problems/**/tests/big-*.in` を .gitignore）。`tests/manifest.json` に sha256 を記録し、`pnpm problems:gen` で再生成する。gen.py は最初から決定的に書き、この移行を「ファイル削除と ignore の追加」だけで済むようにしておく。
- **決定性**: Python の `random` が版をまたいで同じ列を保証するのは `random()` だけ（randint/choice/shuffle/sample は保証外）。gen.py には splitmix64 などの自前の 10 行 PRNG を入れて、それだけを使う。

## 7. 作成チェックリストと完了の定義（DoD）

### 7.1 チェックリスト（1 問ごと）

- [ ] 問題文は 600 字以内。制約に入力・出力・制約・入出力例 2〜3 件・制限時間の注記がある
- [ ] tests/01〜03 が問題文の入出力例と 1 文字も違わない
- [ ] hidden 10 件以上。`hidden-trap-*` が §5 の罠を全部カバーし、`hidden-max-*` が 2 件以上ある
- [ ] gen.py は自前の PRNG と固定シードで決定的。期待値は Python で計算し、小さいケースは brute と一致する。ランダム 300 件以上の stress を通る
- [ ] TLE の罠がある問題は naive.py（必要なら naive.c）を同梱
- [ ] 6 言語の参照解と starter（共通テンプレート）
- [ ] talking_points は 5 枠で、各枠に問題固有の語（制約値・データ構造名）がある
- [ ] requirements 3 件以上、red_flags 2 件以上、面接官メモ（質問と答え、ヒント 2〜3 段）、振り返り用解説（想定解・計算量・素朴解の敗因・別解・言語別の注意）
- [ ] `source.origin` に技法と題材を書いた。類題に気づいたら `known_issues` に記録した。作成中に問題サイトを見ていない
- [ ] サイズ上限（§4.3）を守っている

### 7.2 完了の定義（機械的に確認できるもの）

WP-A を例にする（他の WP は id を入れ替える）。`--only` は完全一致のカンマ区切りか、`-` で終わる接頭辞だけを受け付ける（`selftest.ts:53-55`）。

```bash
cd /home/user/LCI
IDS=cp-0001,cp-0002,cp-0003,cp-0004,cp-0005,cp-0006,cp-0007,cp-0008,cp-0009,cp-0010
pnpm problems:validate                              # エラー 0。CP の警告は「人手レビュー未了」だけ
for d in problems/CP/cp-00{01..10}-*/; do python3 "$d/gen/gen.py" --check || echo "NG $d"; done
                                                    # 再生成が tests/ と完全一致、stress OK
pnpm problems:selftest --only $IDS                  # 60 行すべて 参照解 PASS / starter FAILS
pnpm problems:selftest --only $IDS --naive          # （T4 の後）TLE 罠の問題で naive が 1 件以上 TLE
pnpm problems:selftest --only $IDS --timing         # （T4 の後）全ケースで制限の 50% 以下
for d in problems/CP/cp-00{01..10}-*/; do du -sb "$d/tests"; done   # 6,000,000 以下（T5 の後は validate が検査）
git status --short --untracked-files=all | grep -v ' problems/CP/cp-00\(0[1-9]\|10\)-'
                                                    # 自分の 10 問以外の変更が無い（出力が空）。
                                                    # 他の WP と同じ作業ツリーで作業するなら、WP ごとに worktree を分ける
```

レビューの関門: 別セッションのレビュアーが、1 問 5 段階で「出題できるか・曖昧さ・日本語・既知問題との近さ」を判定する。3 未満は差し戻す（04 G6 と同じ扱い）。

## 9. 未決事項とリスク

- **本番で使う言語**: LCI に C++ は無い。paiza と AtCoder の受験者には C++ が多い。ユーザーが本番で C++ を使うなら、c イメージに g++ を足して Language に `cpp` を加えるのが安い。ただし今の c イメージには gcc しか入っていない（`docker/c.Dockerfile:4`）。練習は本番と同じ言語でするのが原則なので、確認が要る。
- **paiza の制限時間の数値と部分点の扱い**は未確認。セッション時間は、公開されている解答時間中央値から逆算した値にとどまる。
- **TLE 判定の再現性**: Mac の Docker（arm64）は、このコンテナ（x86 Xeon 2.1GHz）より速い可能性があり、素朴解が通ってしまう方向にずれうる。naive の検査は「制限の 1.5 倍以上で落ちる」を基準にして余裕を持たせる。
- **talk-aloud と無言の本番の両立**: 説明しながら解くと時間が 1.3 倍前後かかる（仮定）。試験モードで測った所要時間を、本番の目安として別に記録する。
- **Python の Docker イメージは 3.12、このコンテナは 3.13**（`docker/python.Dockerfile:2`）。速度差は小さいが、selftest の 50% 基準はこの差も吸収するためのもの。
