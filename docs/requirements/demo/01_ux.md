## 0. 結論（先に）

1. **デモが教えるのは「答え」ではなく「話し方と書く順序」。** 答えにあたる参照解・解説・隠しテストは、すでにレビュー画面で開示している（`ReviewNotes.tsx:10-12`, 04 FR-U-15 `04_problems_ux.md:436`）。デモにしかない価値は、要件確認 → 方針宣言 → 説明しながら実装 → 予告してから検証、という**流れの手本**である。章（チャプター）をルーブリックの軸（`evaluation.ts:22-31`）に合わせて固定し、「方針宣言はこう言う」を章単位で見せる教材として作る。
2. **見るのは自分で 1 回解いた後（既定）。** 参照解と同じネタバレ規則に従う。確認ダイアログを経れば解く前にも見られるが、問題に「デモ視聴済み」の印を付け、その後のセッションのレビューに注記する（問題詳細の「開始前に問題文を読みました」と同じ考え方 `problems/[id]/page.tsx:144-146`）。
3. **受け身で眺めるだけにしない仕掛けを 4 つ入れる**: ①解いた後に限るゲート、②レビューの「次の練習」から対応する章へ飛ぶリンク、③章の区切りで止まる「予想してから見る」、④自分のセッションと章ごとに比べる表。終了カードの主ボタンは「もう一度解く」。
4. **同期の単位は「文」。** 1 文 ＝ 字幕の 1 単位 ＝ 音声の 1 単位 ＝ シークの丸め先。コードは「ビート」（数文＋編集のまとまり）で文に結び付け、**ビートの最初の文を言い終えてから打ち始める**（説明先行。R7）。打つ量が説明より多いときは次の文を待たせ、無発話のタイプは 3 秒までに抑える。長さは再生前に確定させる。
5. **動画を使わない判断は正しい。理由は容量だけではない。** コードがテキストのまま残る（コピー・再実行・差分）、文単位で直せる、字幕が音声の元テキストそのもの、の 3 点が効く。容量は台本が 30〜40 KB、音声を事前に合成しても 10 分で 1.2〜1.8 MB（Opus 16〜24 kbps）。画面録画（1 Mbps）なら 75 MB になる。
6. **音声は事前合成を UX 側から推奨する**（作成時、または初回再生時に合成して保存）。長さが確定し、文の途中からシークでき、ピッチを変えずに速度を変えられるため。エンジンの選定は 02 に任せ、本書は §8 で守ってほしい要件だけを書く。
7. **信頼の担保は「全テスト通過」を保存の条件にすることと、それをバッジで見せること。** 説明の誤りは機械では見つけられないので、「Claude 作成・未確認」の表示と、文単位で「ここがおかしい」を付けて作り直しに渡す導線で扱う。
8. **既存部品の再利用**: `CodeTimeline` と `TranscriptPane` は小さな拡張でそのまま使える。`CodeAtT` はサーバ往復で、再生中は 700ms ごとにしか更新しない（`CodeAtT.tsx:99-127`）ので、タイプ演出には使えない。`applyEdit`（`timeline.ts:22-30`、ブラウザから使える `browser.ts:9`）でクライアント側に再構成する新しい部品を作る。
9. **MVP は ALG（stdio）と FE（web）の両方を対象にする。** 基準問題は fe-0001（Pixiv 型、`00_overview.md` §10.3 の受け入れ基準）だから。比較表・章リンク・評価は SHOULD、「ここから自分で書く」・並列再生・シャドーイングは LATER とする。

## 2. デモに入れるもの（章の構成）

章の名前は固定の語彙にし、各章に対応する軸を持たせる。レビューの「次の練習」の軸（`evaluation.ts:134`）から章へ飛べるようにするため。

| # | 章 | 軸 | 見せること | 決め事 |
|---|---|---|---|---|
| 1 | 要件確認 | R1 | 問題の言い換え、制約から設計上の含意を引く（「N=2×10^5 なので O(N²) は 4×10^10 で間に合わない」）、仮定の宣言 | 無言形式（`interviewer_mode: silent`）では、架空の面接官の返答を作らない。「質問するなら〜。返答がない前提で〜と仮定します」の形にする |
| 2 | 方針宣言 | R2・R3 | 手順①②③、計算量、比べた案と捨てた理由、やらないこと | 方針をコメントとしてエディタに書く（話していない時間も画面に方針が残る。実面接でも有効な習慣） |
| 3 | 実装（①②…に分けてよい） | R4・R7 | 宣言した順に実装する。説明が手より先に出る | 説明先行は §3 で構造的に強制する |
| 4 | 検証 | R5 | 「3 番目のサンプルは -1 が出るはず」と予告してから実行する。自作の境界値（例: `K=4, A=[2,2]`）も試す | 実行結果は作成時に実際に実行して保存したものを出す（作り話にしない） |
| (5) | 寄り道: ○○ | R8・R5 | 現実的なミスを 1 回だけ見せる。実行で失敗 → 状況を声に出す → 直す → 再実行で通る | **1 回まで**。`red_flags` または `talking_points` に紐づくミスに限る（例: alg-0001 の「同じ添字を 2 回使うバグ」`alg-0001/problem.md:51-53`）。章名で寄り道だと明示する |
| 6 | 見直し | R6・R2 | 宣言した項目との照合、計算量の再確認、時間があればやる改善（LRU、オーバーフロー等） | 「省略したもの」を言葉にする（fe-0001 の red_flag「宣言した中断処理を…撤回も言語化しない」の手本） |

- **長さ**: 制限時間の 50〜70% を目標とし、70% を超えたら警告、100% を超えたら保存しない。`rubric_hints.time_management` の節目（alg-0001 なら「5 分以内に方針を宣言、10 分以内にサンプル AC」`alg-0001/problem.md:50`）を満たす。画面には「理想化した進行です。本番ではこの 1.3〜1.5 倍かかっても構いません」と添える。
- **話すべきポイント**: 各文に `covers: [tp2]` を付け、すべての `talking_points` に最低 1 回は触れる。プレイヤーでは、触れた時点で一覧に ✓ が付く。

## 3. 同期モデル（ユーザーから見た定義）

**用語**
- **文**: ナレーションの最小単位。`字幕`（表示用。インラインコードを含められる）と、必要なときだけ `読み`（音声用のかな）を持つ。長さ `d`（ms）は音声があればその実測値（前後の無音を除く）、無ければ推定値（1 分 330 字）を使う。
- **編集グループ**: 一続きで打つ編集のまとまり。開始点（アンカー）は「文の終わり」に置く。MVP では文の区切りだけを許し、文の途中の印は SHOULD とする（02 の音声エンジンが語ごとの時刻を返せる場合だけ使う）。
- **ビート**: 1 つ以上の文＋0 個以上の編集グループ＋任意の実行。**チャプター**はビートの並び。

**時刻の決め方**（再生前にすべて確定する。時刻の単位は既存のセッション時計と同じ ms `session.ts:8`）
1. 文は順番に並べる。文と文の間は 300ms、ビートの間は 600ms、章の間は 1,000ms 空ける。ビート b の説明の終わりを `N_b` とする。
2. ビートの最初の編集グループは、**そのビートの 1 文目の終わり**から打ち始める（既定）。2 つ目以降のグループは、作者が指定した文の終わりから始める。
3. 打つ速さ `v` = ビートで打つ文字数 ÷（`N_b` − 最初の打ち始め）とし、8〜30 字/秒（1x のとき）に収める。8 字/秒より遅いと間延びし、30 字/秒より速いと貼り付けに見える（貼り付けは面接で嫌われる操作 `evaluation.ts:54` paste_events）。
4. 1 文字ずつ等間隔に打つ。乱数による揺らぎは入れない（シークの結果を毎回同じにするため）。改行の後に 120ms の間を置き、自動インデントは一度に入れる。削除や置換は、対象範囲を 400ms 選択して見せてから置き換える。
5. ビートの終わり `E_b` = max(`N_b`, 打ち終わり, 実行の終わり)。`E_b − N_b`（無発話でタイプしている時間）は 3 秒までなら警告、6 秒を超えたら保存しない。これで「黙って書く」デモは作れなくなる。
6. 実行は「実行中…」を 1,200ms 表示してから、結果を出す。結果を説明する次の文はその後に始まる。

**再生**
- 時計の主は上で確定したタイムライン。音声はタイムライン上の決まった時刻に始める。音声のデコードが遅れたら、時計を止めて待つ（**字幕と音声は絶対にずらさない**）。方式はレビュー画面の内部時計（`ReviewScreen.tsx:124-144`）と、メディアからの rAF 報告（`VideoPane.tsx:13`）の組み合わせと同じでよい。
- **一時停止して再開すると、文の途中から続きを再生する**（文の頭には戻らない）。
- **速度** s（0.75 / 1 / 1.25 / 1.5 / 2）にすると、すべての時刻が 1/s 倍になる。音声はピッチを変えずに s 倍速で流し、打つ速さも s 倍にする。変更は 300ms 以内に反映し、文の途中のまま続ける。字幕だけで追うなら 1.25x が上限の目安（1x の 330 字/分は読める速さだが、2x の 660 字/分は黙読の速さを超える）なので、速度メニューに注記する。
- **シーク**: ドラッグ中は、その時刻ちょうどのコードを連続して表示する（打っている途中も見える）。指を離したら、その時刻以前で最も近い区切り（文・編集グループ・実行の開始）に丸めて再生を続ける。音声が文の途中から始まって意味が取れない、という状態を作らない。
- **コードの状態**は時刻だけで決まる関数 `code(t)` とする（t より前の編集をすべて当て、打っている最中のグループは打ち終えた分だけ当てる）。
- **表示の切り替え**（「文字ごと」/「まとめて」）、**消音**、**音声の有無**のいずれも、タイムラインの長さと時刻を変えない。「まとめて」ではグループの開始時刻にグループ全体を一度に出す。音声を作り直したときだけ長さが変わり、それは新しい版として扱う。

## 4. 機能要件（FR-D）

優先度: MUST（MVP）/ SHOULD（MVP 直後）/ LATER（必要が見えたら）

### 4.1 入口・ゲート

| ID | 要件 | 優先 |
|---|---|---|
| FR-D-01 | デモは（問題, 言語, 版）を単位とする。版は保存したら変えない。作り直すと新しい版になる。既定で表示するのは最新の「検証済み」の版 | MUST |
| FR-D-02 | 専用ルート `/problems/[id]/demo?lang=&v=` で再生する。レビュー画面の再生ワークスペースには埋め込まない（時計が 2 つになり、Space がどちらを動かすのか曖昧になる） | MUST |
| FR-D-03 | 入口は (a) レビュー画面の解説の直前に置くデモカード、(b) 問題詳細の「前回の記録」パネルにあるリンク、の 2 つ | MUST |
| FR-D-04 | ゲート: その問題の終了済みセッションが 0 件なら、プレイヤーの代わりにゲート画面を出す（判定には問題詳細と同じ `buildRecords` を使う `problems/[id]/page.tsx:25-26`）。「解かずに見る」は確認ダイアログを経て許可し、視聴したことを記録して、問題に「デモ視聴済み」を付ける。以後のセッションのレビューに「デモ視聴後のセッション（R1/R2 は本番より有利）」と注記する | MUST |
| FR-D-05 | 既定の言語は「入口のセッションの言語 → その問題の最新セッションの言語 → `languages` を D13 の順に並べた先頭（TS/JS → Python `00_overview.md:33`）」の順に決める。言語の切り替えには、デモがある言語と「この言語で作る」を並べる | MUST |
| FR-D-06 | 問題一覧のカードに「デモあり / 視聴済み」を小さく出す | SHOULD |

## 7. アクセシビリティ

- 字幕を常に出し、全文の一覧と台本ビューも用意する（WCAG 1.2.1 / 1.2.2）。音声を自動で流さず、消音できる（1.4.2）。タイプ演出は 5 秒を超えて動き続ける内容なので、一時停止できなければならない（2.2.2）。
- エディタは読み取り専用の Monaco にし、`aria-label` を「03:12 時点のデモのコード（読み取り専用）」とする。**打った文字は読み上げない**（aria-live off）。ユーザーが章を移動したときだけ、`role=status` で「3 実装 02:30 から」と知らせる。
- `prefers-reduced-motion` では「まとめて」表示にし、スクロールも瞬時にする。
- フォーカスは通常の DADS 二重リングを使う（面接画面の例外 `data-session` は付けない。録画しない画面のため）。
- 色: 章の帯は無彩色＋文字（X3）。実行結果はシステム状態の色（X2: ✓ ✕＋文字）。**評価の色（eval-*）はデモでは使わない**（評価結果ではないので、X1 の意味を薄めない）。話すべきポイントの ✓ も無彩色にする。
- 押せる部分は 24px 以上（X5）。フォーカスの順は 操作部 → タイムライン → コード → 字幕 → 左の列 → 右の列。

## 8. 容量と音声（UX 側の要件。エンジンは 02 が決める）

| 方式 | 10 分 | 15 分 | 根拠・注記 |
|---|---|---|---|
| 台本（字幕＋読み＋編集＋実行結果の JSON） | 30〜40 KB | 45〜60 KB | 1 分 330 字 × 字幕と読みの 2 系統 ≈ 20 KB、編集は参照解の 2〜4 倍（fe-0001 の参照解は 2,444 B、alg-0001 の Python は 374 B） |
| ＋事前合成の音声 Opus 16 / 24 kbps（モノラル） | 1.2 / 1.8 MB | 1.8 / 2.7 MB | 120 / 180 KB/分 |
| ＋事前合成の音声 AAC-LC 48 kbps | 3.6 MB | 5.4 MB | iPhone 実機でも再生したいときの候補 |
| 再生のたびに合成 | 0 B | 0 B | 下の表の UX 上の欠点がある |
| （参考）画面録画 1 Mbps | 75 MB | 112 MB | FR-C-53 の予算（`01_capture.md:87`） |

規模の見積もり: 解いた問題 100 問 × 1.5 言語のデモを作ると、Opus 24 kbps で約 300〜400 MB、台本だけなら約 6 MB になる。画面録画の 1 セッション（20 分 ≤350 MB）とほぼ同じなので、事前合成で問題ない。

| UX 上の観点 | 事前合成 | 再生のたびに合成 |
|---|---|---|
| 長さが再生前に決まる（タイムライン・シーク） | ◯ | ✕（推定値なので、再生中に伸び縮みする） |
| 文の途中から再開・シークする | ◯ | ✕（文の頭からやり直す） |
| ピッチを変えずに速度を変える | ◯（`playbackRate`） | △（話す速さを変えると、その文を頭から言い直す） |
| 声がいつも同じ | ◯ | △（マシンの音声に左右される） |
| 再生を押してから音が出るまで | ◯ | △ |
| 容量 | 1 本 1〜3 MB | 0 |

→ **推奨: 事前合成**（作成時、または初回再生時に合成してキャッシュする）。「音声だけ削除」できれば、容量の心配も解ける。

**音声への要件（02 に渡す）**
- V-01 オフラインで再生できる。合成もローカルで済むほうが望ましい（ローカル完結の原則 `04_problems_ux.md:357`）。
- V-02 文ごとの開始・終了時刻を ±20ms の精度で取れる。前後の無音は 100ms 以下に削る。1x で 1 分 300〜350 字、文の間は 300ms。
- V-03 1 本のデモの中では同じ声を使う。どの声を使ったかを版に記録する。
- V-04 0.75〜2x でピッチが変わらない（Chrome の `preservesPitch` で足りる形式）。D15（Chrome のみ `00_overview.md:35`）を前提にする。
- V-05 音量をそろえる（目安 −16 LUFS）。BGM・効果音は入れない。
- V-06 読みの辞書を使う: `dict`→ディクト、`Map`→マップ、`O(N log N)`→オーダー エヌ ログ エヌ、`N=2×10^5`→エヌは 2 かける 10 の 5 乗、`K - x`→ケー マイナス エックス、`-1`→マイナスいち、`AbortController`→アボートコントローラー、`TTL`→ティーティーエル。記号をそのまま読ませない。**コードを 1 文字ずつ口述しない**（意図と、鍵になる識別子だけを言う）。
- V-07 読み間違いを指摘された文だけを作り直せる（全体を合成し直さない）。
- V-08 合成できないときは、字幕だけで再生できる状態で保存する（FR-D-53）。

読みの辞書は、文字起こしの `initial_prompt`（`session.ts:48`）や話すべきポイントの検出（`metrics.ts:44,66`）と同じ用語表から作る。デモが話す言葉と、ユーザーの発話を照合する言葉をそろえるため。

## 11. ユーザー（Nico）への質問（3 件）

1. **解く前にデモを見られるようにしますか？**
   推奨: 既定は「1 回解いてから」。確認を経れば解く前にも見られるが、問題に「視聴済み」が付き、以後のセッションのレビューに注記が出る。理由: 実装済みの問題は 27 問しかなく（`README.md:58`）、初見で解く機会は 1 問に 1 回しかないため。
2. **デモに「意図的なミスと修正」を 1 回入れますか？**
   推奨: 入れる（1 回まで、red_flags に由来するものだけ、章名で明示）。理由: R8（復帰力）と R5（テストで見つける）の手本は、ミスが無いデモでは見せられない。紛らわしさは、章名と、失敗する実行を実際に見せることで抑える。
3. **iPhone でデモを見たい（聞きたい）ですか？**
   推奨: MVP では Mac のブラウザだけにする（狭い幅のレイアウトには対応する）。必要になったら「単体 HTML として書き出す（約 3 MB、AirDrop で持ち出せる）」を足し、そのとき音声の形式を AAC にする。理由: アプリは localhost で動いているので、iPhone から見るには LAN への公開が必要になり、守るべき範囲が広がる。

## 12. 他のレビュアーとそろえること

**02（MCP ツールと音声エンジン）へ**
- 台本は「章 → ビート → 文（字幕・読み・covers）＋編集グループ（文の終わりをアンカーにする）＋実行」の形にし、アプリ側で Event[] と発話セグメントに組み立てられるようにする（§9）。
- 編集は「テキストを探して置き換える」アンカー方式で書けるようにし、組み立てたときの最終コードが検証したコードと一致すること。
- 保存は「下書き → 検証 → 公開」の 3 段階にする。FR-D-31〜36 の検査結果（長さ、無発話の秒数、網羅、テストの結果）は文章で Claude に返し、不合格なら公開しない。アプリには下書きの進み具合を見せる。
- 実行ビートは保存時に実際に実行して、出力を保存する。web は保存時に判定できない（ブラウザでしか判定できない）ので「判定待ち」で公開し、アプリで開いたときに判定する。
- 版は保存後に変えない。問題のハッシュを記録する。音声の要件は V-01〜08、1 本 15 分で 3 MB 以下が目安。
