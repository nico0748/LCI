# 模範解答デモ 決定ログ（2026-10-25）

依頼: 「模範解答をライブコーディング演出で音声付き解説してくれる機能（動画はいらない→容量増えるから）。MCP サーバで Claude に解説音声とそれに合わせてライブコーディングをデモンストレーションする機能」

2 本の批評（`01_ux.md` 体験設計、`02_mcp_tts.md` データ形式・MCP・音声）を統合し、食い違いをここで決める。実装はこのファイル → 02（技術）→ 01（画面）の順に従う。契約は `packages/demo/src/schema.ts` と `types.ts`。

## 方針

- デモの役割は「参照解を見せる」ことではなく（参照解・解説はレビュー画面で既に開示している）、**どの順で何を話しながら書くか** の手本を見せること。章はルーブリック軸に対応した固定の語彙にする（01 §2）。
- 動画は作らない。**台本（テキスト＋コード操作）を保存し、アプリがタイプ演出と時刻を決定的に組み立てる**。音声は台本から作り直せる派生キャッシュ。
- Claude は内容だけを書く。**行・列の位置も時刻も書かせない**（02 §2–4）。

## 食い違いの解消

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| D1 | 台本の単位 | 02 の `chapter → step` を採る。step は 1 区間のナレーション（`say`、複数文可）＋コード操作＋任意の実行。01 の「ビート」= step。step 内の 2 つ目以降の編集グループを文の終わりに置く機能は LATER | スキーマを単純に保ち、Claude の書き損じを減らす。文単位の字幕は say を句点で分けて表示すればよい |
| D2 | コード操作 | `replace {old,new}`（old は一意一致）／`append`／`write` の 3 種。アプリが打鍵に展開し既存の `edit` イベントにコンパイルする | 02 §2。Claude の Edit ツールと同じ意味論で、失敗が具体的に直せる |
| D3 | 章の語彙 | `requirements / plan / implement / test / detour / review`。detour（寄り道: 現実的なミス 1 回→実行で失敗→直す→通る）は任意で 1 回まで、red_flags か talking_points に紐づくもの | 01 §2。寄り道を入れないと「検証して直す」手本（R5・R8）が見せられない。2 回以上は混乱する |
| D4 | 打鍵の速さ | 1x で 8〜25 字/秒に収める。乱数の揺らぎは入れない（シーク結果を毎回同じにする） | 01 §3 と 02 §4.2 の中間 |
| D5 | 無発話のタイプ | 3 秒超で警告、**8 秒超で保存しない** | 01 は 6 秒、02 は 15 秒。説明先行（R7）の手本として 15 秒は長すぎ、6 秒は長いブロックを打つ step で Claude が直しきれない |
| D6 | 長さ | 目標は制限時間の 50〜70%。70% 超で警告、100% 超（または 20 分超）で保存しない | 01 §2・02 §4.2 で一致 |
| D7 | 対象の問題 | **MVP は stdio / unit 問題だけ**。web 問題（FE）は v1.1（ブラウザ側での検証を足してから） | サーバで web 判定ができない（`packages/runner/src/judge.ts:228`）。今回は競プロ系の問題を増やすので stdio が主になる |
| D8 | 検証と保存 | 保存前に必ず検証（スキーマ→操作適用→各実行ステップと最終コードの判定→タイミング→デモ自身の指標→talking_points/requirements 網羅→ナレーション lint）。最終コードが隠しテストを含めて全通過しない版は保存しない。実行結果は保存時の実測を記録して再生する | 01 FR-D-31、02 §5 |
| D9 | 実行環境 | 検証の実行は Docker ランナー。`LCI_RUNNER=fake`（ホストで隔離なしに実行）はテストでだけ `LCI_DEMO_ALLOW_FAKE=1` で許可する。Docker が無いときは「Docker を起動してから再度保存してください」と Claude に返す | 02 F8。Claude が書いたコードをホストで直接走らせない |
| D10 | 音声エンジン | **macOS `say` を保存後にアプリ側で区間ごとに合成**し、AAC 32 kbps モノラル m4a（内容ハッシュ名）で保存する。12 分で約 3 MB（録画 1 本の約 1/30）。合成できない環境（Linux・`say` 無し）では**字幕のみ**で再生する。Web Speech API は v1.1 | 02 §7。容量を抑えつつ、長さを事前に確定でき、文の途中からのシークと速度変更（ピッチ維持）ができる |
| D11 | 読み | `say.reading`（かな）と `glossary` と組み込み辞書（`O(N log N)`、`10^5`、`dict` など）で読みを作る | 01 §8 V-05、02 §7.3 |
| D12 | 再生の時計 | 区間内は音声が主、区間外は仮想時計（DemoClock）。音声の読み込みが遅れたら時計を止めて待つ。速度・タイプ演出・消音はタイムラインを変えない | 01 §3・02 §8 で一致 |
| D13 | 置き場所・URL | 保存は `data/demos/<problem_id>/<language>/<demo_id>/`（git 管理外、版は 10 件まで）。画面は `/problems/[id]/demo?lang=&demo=`。MCP の保存結果はこの URL を返す | 01 FR-D-02（レビューの再生ワークスペースに埋め込むと時計が 2 つになる） |
| D14 | ネタバレ | 台本と音声は `reveal=1` のときだけ返す。画面は、その問題の終了済みセッションが 0 件ならゲートを出し、確認ダイアログを経て「解かずに見る」を許可する | 01 FR-D-04。視聴済みの記録とレビューへの注記は SHOULD |
| D15 | 録画中 | 録画中のセッションがあるときはデモの API を 409 にし、音声を鳴らさない | 02 F17（エコーで文字起こしが汚れる） |
| D16 | 作成経路 | MVP は MCP だけ（`get_problem_for_demo` → `validate_demo_script` → `save_demo_script`）。アプリ内の API キーで作る経路は v1.1（同じガイド・スキーマ・検証器を使う） | 02 §6.4 |
| D17 | 依存関係 | 新パッケージ `@lci/demo`（core + runner に依存）。mcp-server が `@lci/demo` に依存してよい、と `docs/API_CONTRACT.md` に追記する | 02 結論 8 |
| D18 | 信頼の表示 | ヘッダに「✓ 全テスト通過 8/8」と「Claude 作成・未確認」を出す。版の切り替えと削除を置く | 01 FR-D-40〜42 |

## API（契約。型は `packages/demo/src/types.ts`）

| メソッド | パス | 返すもの |
|---|---|---|
| GET | `/api/demos?problem=<id>` | `DemoSummary[]`（ネタバレなし、新しい順） |
| GET | `/api/demos/<demo_id>?reveal=1` | `DemoDetail`（台本・コンパイル結果・音声マニフェスト）。reveal が無ければ 403 |
| GET | `/api/demos/<demo_id>/audio/<key>` | 音声区間（audio/mp4）。キャッシュ可 |
| POST | `/api/demos/<demo_id>/audio` | 音声合成を始める（202）。合成できない環境なら 409 と理由 |
| DELETE | `/api/demos/<demo_id>` | 版を削除。`?audio_only=1` なら音声だけ |

録画中のセッションがあるときは上のすべてが 409。

## MCP ツール（02 §6）

`list_problems` / `get_problem_for_demo` / `validate_demo_script`（read-only）/ `save_demo_script` / `list_demos` / `get_demo_script` / `delete_demo`（destructive）、プロンプト `author_demo`、リソース「オーサリングガイド」。

## MVP の範囲

- MUST: 01 の FR-D-01〜05, 10〜18, 30〜36, 40〜42, 50〜53 と、02 §12 の MVP。
- SHOULD（できれば今回）: FR-D-37（寄り道）, 45（デモ自身の指標表示）, 60（自分のセッションとの比較表）。
- LATER: web 問題、Web Speech、アプリ内生成、文単位の指摘、シャドーイング、並べて再生。
