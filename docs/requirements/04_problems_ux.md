## 1. 目的

- 本書は「約500問の問題バンク（Scope A）」と「練習アプリの画面・体験（Scope B）」の要件を定義する。
- 利用者像は brief の通り、日本語話者の就活生（Web/セキュリティ志望）が **「説明しながら書く」** 形式の面接に備えること。したがって問題バンクの価値は「解けるか」ではなく **「話すべき設計判断（talking_points）が明示され、録画後に Claude が評価できる構造になっているか」** にある。
- Pixiv 実試験（検索フォーム＋貧弱サーバー＋キャッシュ戦略を説明、20分、相手は無反応、質問は可、Web検索不可）が基準形。問題バンクの中心（最大カテゴリ）はこの「小さな機能を要件の裏にある非機能要件を語りながら作る」型にする。
- M3（エムスリー）の試験内容は未入手。公開体験記（onecareer / 外資就活）は「コーディングテストあり」としか読み取れず、形式は不明（要確認）。本書では **「医療系Webらしい業務データ処理（CSV/集計/日付/権限）＋実務寄りのWebタスク」を M3 型と仮定** し（仮定）、後から差し替え可能なタグとして扱う。

## 2. 問題バンク分類と目標問題数（表）

### 2.1 設計方針

1. **「実装型」を主軸、「アルゴリズム型」は従**。Pixiv 型試験で問われるのは計算量ではなく「要件の読み替え・非機能要件への配慮・説明の筋道」。LeetCode 互換の問題で 500 問埋めると、このアプリ固有の価値（発話とコードの対応評価）が死ぬ。
   - **改訂（2026-10-25、`05_cp_problems.md` §2.3）**: 本番の大半が paiza C〜A・AtCoder ABC-C 相当の標準入出力型だったため、競技プログラミング形式（CP）を 150 問（30%）の最大カテゴリとして新設した。CP でも talking_points（計算量・境界・テストの立て方の言語化）は必須で、発話とコードの対応評価という価値は変えない。
2. **すべての問題に talking_points を必須化**。アルゴリズム問題でも「なぜこのデータ構造か」「計算量」「エッジケース」を言語化することを採点対象にする。
3. **時間枠は 15/20/30/45 分の 4 種**。Pixiv 実績の 20 分を標準（約 45%）、15 分はウォームアップ、30/45 分は設計寄り・デバッグ寄り。
4. **言語は問題カテゴリ単位で宣言**。フロント系は HTML/CSS/JS/TS のみ、SQL は言語非依存、C/Rust は低レイヤ・アルゴリズム・セキュリティ実装に集中させる。7 言語×500 問の参照解を全部用意するのは非現実的（§4 参照）。

### 3.3 本文セクション（Markdown、frontmatter の下）

1. `## 問題文` — 面接官が口頭で言う粒度。1 画面に収まる長さ（目安 250 字以内）。
2. `## 制約` — 入出力形式、禁止事項（Web 検索不可など）、使用可能ライブラリ。
3. `## 面接官メモ（非公開）` — 想定される質問と答え、ヒントの出し順。`interviewer_mode: followup` のとき TTS/テキストで提示する台詞を含む。
4. `## 振り返り用解説（終了後のみ表示）` — 想定解答方針。Pixiv 記録の「想定解答の方針」に相当。

### 3.4 スキーマ上の注意（批判的コメント）

- `talking_points` と `rubric_hints` を分けている理由: 前者は「言ったかどうか」を文字起こしから検出する機械的チェック、後者は Claude の裁量評価の指針。混ぜると評価が不安定になる。
- `languages` は **参照解＋テストが実在する言語のみ**。「7 言語対応」をメタデータ上で宣言するだけの問題を作らない（§4.4 のゲートで強制）。
- `hidden_tests` は候補者には見せない。ただし終了後のレビュー画面では結果を公開する（学習効果のため）。
- SYS カテゴリは `hidden_tests` を空にし、代わりに `rubric_hints.checklist`（言及すべき構成要素）を持つ。
- `time_limit` の 15/20/30/45 以外は許容しない（UI のプリセットと一致させる）。

## 4. 生成・品質保証パイプライン

### 4.1 正直な前提

**LLM に 500 問を書かせると、相当数が「それらしいが面接問題として弱い」ものになる。** 典型的な劣化は: (a) 問題文が長く曖昧、(b) talking_points が一般論（「エッジケースを考慮する」）、(c) 隠しテストが参照解に過学習し別解を落とす、(d) 同じ題材の言い換え重複、(e) 難易度ラベルの自己申告が甘い。これらは自動テストでは検出しにくい（(c) を除く）。

したがって **段階的に品質を担保する二層構成** を採る。

| 層 | 数 | 作り方 | 品質保証 |
|---|---|---|---|
| Core | 100 | 人手で起案 or LLM 下書き→人手で全文書き直し。各カテゴリ最低 8 問、FE は 25 問 | 人手レビュー 2 名相当（本人＋Claude をレビュアー役にした別セッション）、実際に 1 回タイマー付きで解く |
| Generated | 400 | Core をテンプレート（few-shot）にして LLM 生成 | §4.3 の自動ゲート全通過＋サンプリング人手確認（各バッチ 10%） |

v1 リリース時点では **Core 100 問＋Generated のうちゲート通過分のみ** を公開し、500 は到達目標として扱う（§10）。

### 4.2 生成フロー

```
[種（seed）定義] → [LLM 生成（問題文/制約/talking_points/テスト/参照解）]
   → [静的ゲート] → [実行ゲート] → [重複ゲート] → [LLM 相互レビュー]
   → [tier=generated で登録] → [使用ログに基づく事後評価] → [昇格/降格]
```

1. **種定義**: カテゴリ×難易度×nfr タグ×題材ドメイン（イラスト投稿/医療データ/EC/通知 等）の組合せ表から未充足セルを選ぶ。これにより題材の偏りと重複を構造的に防ぐ。
2. **生成**: 1 問あたり「問題文→talking_points→テスト→参照解」の順に **分割生成**。一括生成すると参照解に合わせて問題文が歪む。
3. **参照解は 2 本**: 主解と別解（別の設計選択）を生成し、両方がテストを通ることを要求する。テストの過学習（上記 (c)）の最も効く対策。

### 4.3 品質ゲート（自動）

| ゲート | 内容 | 落ちた場合 |
|---|---|---|
| G1 スキーマ | frontmatter 必須項目、time_limit 列挙値、languages ⊆ 参照解の存在する言語 | 即破棄 |
| G2 実行 | 各言語の参照解（主・別解）を Docker で実行し hidden_tests 全通過。さらに **「空実装」「常に同じ値を返す実装」がテストを落とすこと** を確認（テストの有効性検査） | 再生成 1 回、ダメなら破棄 |
| G3 時間 | 参照解の行数・トークン数が time_limit に対する上限内（例: 20 分なら主要ロジック 60 行以内） | difficulty/time_limit を再割当 |
| G4 重複 | 問題文＋talking_points の埋め込み類似度。閾値超えで既存問題と突合（閾値は Core 100 問の相互距離から決める） | 破棄 or タグ統合 |
| G5 talking_points 具体性 | 各 talking_point が問題固有の名詞（API 名/データ構造/制約値）を含むか。一般論のみは NG | 再生成 |
| G6 相互レビュー | 別プロンプトの LLM が「面接官として 20 分で出題できるか」「曖昧さ」「日本語の自然さ」を 5 段階評価。3 未満は人手キューへ | 人手キュー |
| G7 セキュリティ | SEC カテゴリは参照解に脆弱パターン（innerHTML 直挿し、文字列結合 SQL）が無いことを静的検査（semgrep 等）（要確認: ルール整備工数） | 破棄 |

### 4.4 事後評価（使用ログからの昇格・降格）

- 練習セッションで「ユーザーが問題文に質問した回数」「途中離脱率」「Claude 評価で『問題文が曖昧』と出力された回数」を問題ごとに集計。
- 閾値を超えた generated 問題は `draft` に降格し一覧から隠す。逆に 10 セッション以上で問題なしなら Core 候補として人手レビューに回す。
- ローカル専用アプリのため集計はユーザー 1 人分しかない。**単独利用では統計的昇格は機能しない**（リスク §9）。v1 では「ユーザーが問題に 👎 を付けたら隠す」程度に簡略化する。

### 4.5 生成に関する補足判断

- 生成は Claude API（またはローカル Claude Code の一括セッション）で行う。費用と速度は本書の範囲外だが、500 問×分割生成×2 解×7 言語の最悪ケースは現実的でないため、**言語は問題あたり平均 2.5 言語** を目標にする（表 §2.2 の対応言語は「許容言語」であり全問提供ではない）。
- 日本語問題文の品質は人手でしか担保できない。Core 100 問は全文を人が書き、generated は G6 でスクリーニングするが、**生成問題の日本語の不自然さは残る前提** で、UI 上に tier バッジを表示してユーザーに期待値を伝える。

## 5. 画面一覧とフロー

### 5.1 画面一覧

| ID | 画面 | 役割 |
|---|---|---|
| S0 | 初回セットアップ | カメラ/マイク/画面共有の許可、Docker と文字起こしエンジンの疎通確認、MCP 接続テスト |
| S1 | ホーム / 問題選択 | 今日の推奨問題、カテゴリ・難易度・時間でフィルタ、前回の続き |
| S2 | セッション開始前（ブリーフィング） | 問題文の閲覧、言語選択、録画デバイスのプレビュー、カウントダウン |
| S3 | 面接セッション | タイマー、問題、エディタ、プレビュー/コンソール、録画・文字起こし表示 |
| S4 | 終了 → 評価待ち | 録画の保存、ログの整合性チェック、Claude への解析依頼状態 |
| S5 | レビュー | 動画＋同期文字起こし＋コードタイムライン＋Claude フィードバックのピン |
| S6 | 履歴 / 成長ダッシュボード | セッション一覧、カテゴリ別スコア推移、弱点タグ、再挑戦導線 |
| S7 | 設定 | 言語・テーマ・ショートカット・保存先・録画品質・面接官モード |

### 5.2 主フロー

```
S1 ホーム ─選択─▶ S2 ブリーフィング ─開始─▶ S3 セッション ─終了/時間切れ─▶ S4 評価待ち ─完了─▶ S5 レビュー ─▶ S6 履歴
   ▲                                                                                        │
   └──────────────────────────── 再挑戦（同問題 or 類似問題） ◀─────────────────────────────┘
```

- S2 → S3 の遷移は **1 操作（Enter）**。開始後は S3 からの離脱手段を「終了」のみに制限し、誤操作でセッションが壊れないようにする。
- S3 → S4 は「終了ボタン」「時間切れ」「異常終了（クラッシュ）」の 3 経路。異常終了時も録画・ログを部分保存し S4 で「部分データで評価」を選べる。
- S4 で Claude（MCP）が未接続なら、評価を後回しにしてレビュー画面を「自己レビューモード」（動画＋タイムラインのみ）で開ける。評価は後から追加可能。

### 5.3 面接官モード（S2 で選択）

| モード | 挙動 | 根拠 |
|---|---|---|
| `silent`（既定） | 相手は無反応。候補者が一方的に話す。Pixiv 実試験の形式 | pixiv_problem.md |
| `followup` | 所定タイミング（例: 残 8 分・残 3 分、または 60 秒以上無言）で面接官メモの質問をテキストで提示。TTS は任意 | §6.2 で評価 |

## 6. 画面ごとの構成要素

### 6.1 S1 ホーム / 問題選択

- 上段: 「前回の続き」「今日の 1 問（弱点タグから選出）」「Pixiv 形式 20 分をもう一度」の 3 カード。
- 中段: フィルタ（カテゴリ / 難易度 / 時間 / 言語 / tier / 未着手・再挑戦）。フィルタは URL に保持し再現可能。
- 問題カード: タイトル、カテゴリ色、L1–L4、時間、対応言語アイコン、tier バッジ（core は無印、generated は「自動生成」と明記）、過去のベストスコア。
- **問題文はホームでは見せない**（開始前に読んでしまうと「初見で要件を読み解く」練習にならない）。タイトルも抽象化オプション（「FE-L2 / cache」のみ表示）を設定で選べる。
- キーボード: `/` で検索、`j/k` で移動、`Enter` で S2。

### 6.2 S3 面接セッション画面

レイアウト（12 カラムグリッド、デスクトップ 1440px 基準）:

```
┌──────────────────────────────────────────────────────────────┐
│ ヘッダ(40px): 問題名 | 残り時間 ●REC 文字起こし状態 | 終了     │
├───────────────┬──────────────────────────────┬───────────────┤
│ 問題ペイン     │ Monaco エディタ               │ プレビュー /   │
│ (3col, 折畳可) │ (6col, タブ=ファイル)          │ コンソール     │
│ 問題文/制約    │                              │ (3col)        │
│ メモ欄(任意)   │                              │ テスト実行結果 │
├───────────────┴──────────────────────────────┴───────────────┤
│ 文字起こしストリップ(1行, 直近 1 文のみ, 折畳可)   面接官メッセージ │
└──────────────────────────────────────────────────────────────┘
```

構成要素と設計判断:

| 要素 | 仕様 | 判断理由 |
|---|---|---|
| タイマー | 残り時間を mm:ss。残 5 分で色変化、残 1 分で 1 回だけ控えめな音。進捗バーは無し | 常時点滅・秒単位の強調は不安を煽る。実試験は面接官が口頭で残り時間を告げる程度 |
| 録画インジケータ | 小さな ● のみ。カメラ映像のセルフビューは **既定で非表示**（設定で PiP 表示可） | 自分の顔を見続けると説明に集中できない。実面接でも自分の映像は小さい |
| 文字起こしストリップ | 直近 1 文のみ、淡色、1 行。全文は見せない。誤認識の修正 UI は置かない | 自分の発話が文字で流れるのを見ると言い直しが増え、不自然になる。ただし「録れている」確認は必要なので 1 行残す |
| 問題ペイン | 開始時に表示、`Cmd+1` で折畳。メモ欄はプレーンテキストで、編集ログに含める | 要件の読み返しは実面接でも可能 |
| エディタ | Monaco、言語は S2 で確定。LSP 補完は言語ごとに ON/OFF（設定）。**AI 補完は無し** | 面接環境は補完が弱いことが多い。既定は構文補完のみ |
| プレビュー / コンソール | `browser` runtime は iframe サンドボックス＋モック API、それ以外は stdout/stderr。`Cmd+Enter` で実行 | Pixiv 型はプレビュー必須。モック API は latency を再現 |
| テスト実行 | 候補者が任意に実行できるのは **公開サンプルのみ**。hidden_tests は終了後 | 面接でテストが与えられることは稀 |
| 面接官メッセージ | `followup` モード時のみ、右下にトースト風で 1 件表示。既読まで残る | 後述 |
| 編集ログ収集 | Monaco の `onDidChangeModelContent` と `onDidChangeCursorSelection` から 500ms 間隔で {file, range, symbol（軽量パーサ or LSP documentSymbol）} を記録。発話セグメントとタイムスタンプで結合 | brief の中核要件。レビュー画面の同期に必須 |

**面接官ペルソナ＋TTS の評価**:

- 利点: Pixiv 形式以外（面接官が合いの手を入れる会社）の練習になる。無言が続いたときの再起動のきっかけになる。
- 問題点: (1) TTS の声が被ると文字起こしが自分の発話と TTS を混同する（エコーキャンセルが必要）、(2) 質問タイミングが不自然だと「邪魔」になる、(3) 実試験の Pixiv は無反応形式なので、既定で ON にすると練習対象が変わる。
- 結論: **v1 はテキスト提示のみ、TTS は COULD**。発火条件は「固定時刻」＋「60 秒無言」の 2 種に限定し、質問文は問題ファイルの面接官メモから取る（LLM によるリアルタイム生成は v1 では行わない。遅延と品質の不確実性が高い）。

### 6.3 S4 終了 → 評価待ち

- 終了直後に **「今の手応え」を 3 択＋一言で自己申告**（30 秒以内）。後で Claude 評価との差分を示す（自己認識のずれが面接対策では重要）。
- 進捗: 録画 mux → 文字起こし確定（最終パス）→ ログ整合性 → Claude へ送信 → 解析中。各工程の失敗は個別にリトライ可能。
- Claude 解析は数分かかり得るため、待っている間に「自己レビュー（S5 の動画＋タイムラインだけ）」を開ける。評価が来たら S5 にピンが追加される。

### 6.4 S5 レビュー画面

```
┌────────────────────────────┬─────────────────────────────┐
│ 動画（画面収録＋カメラ PiP）  │ コードタイムライン・スクラバ    │
│                            │  ├ ファイル別レーン            │
│                            │  ├ 発話セグメント              │
│                            │  └ Claude ピン ◆◆◆            │
├────────────────────────────┼─────────────────────────────┤
│ 同期文字起こし（クリックで飛ぶ）│ その時点のコード（差分表示）    │
├────────────────────────────┴─────────────────────────────┤
│ Claude 総評: 説明力 / 設計方針 / 正確性 / 時間配分 / talking_points 達成 │
└──────────────────────────────────────────────────────────┘
```

- **時刻を唯一の主キー**にして、動画・文字起こし・コード状態・ピンをすべて同期。どのペインをクリックしても他が追従する。
- Claude ピンは `{t, kind: praise|issue|question, text, related_talking_point?, related_range?}`。ピンをクリックすると「その瞬間の発話」と「その瞬間のコード」が並ぶ。
- talking_points チェックリスト: 言及あり/なし/曖昧 を文字起こし根拠付きで表示。「言及なし」は強調しすぎない（§7）。
- 隠しテストの結果をここで初めて開示。
- 「次にやること」は最大 3 件。10 件並べると読まれない。
- エクスポート: Markdown（Obsidian 等へ）＋ JSON。

### 6.5 S6 履歴 / 成長ダッシュボード

- セッション一覧（日付・問題・時間・4 軸スコア・自己申告との差）。
- カテゴリ×難易度のヒートマップ、talking_points 達成率の推移、「無言時間比率」「開始から最初のコード編集までの時間」など発話×コードならではの指標。
- 弱点タグ上位 3 → ホームの「今日の 1 問」に反映。
- グラフは控えめ。数値が少ない初期（セッション 5 回未満）はグラフを出さず文章で表示する。

## 7. デザイン原則

1. **セッション中は静か**: 動くものはタイマーと文字起こし 1 行だけ。通知・バッジ・アニメーションを禁止。色は無彩色＋アクセント 1 色。
2. **不安を増やさない**: 残り時間は見えるが煽らない。文字起こしの誤認識を本人に見せすぎない。スコアは終了後にのみ表示し、セッション中にリアルタイム採点はしない。
3. **キーボードファースト**: 開始・実行・終了・ペイン切替・ファイル切替をすべてショートカットで。マウス必須の操作をゼロにする（Monaco 内は Monaco 既定に従う）。
4. **本番再現性 > 便利さ**: AI 補完なし、Web 検索なし（問題で許可されていれば外部リンクのみ）、自分で質問する代わりに「質問ログ」を残す。
5. **評価は根拠付き**: Claude の指摘は必ず時刻とコード範囲に紐づける。根拠のない総評は表示しない。
6. **ローカル完結の安心感**: 録画・文字起こし・評価のどこまでがローカルかを S0 とレビュー画面に明示。外部送信（Claude API 経由の場合）は毎回ではなく初回に説明し同意を得る。

### 7.1 レイアウトグリッド

- 12 カラム、ガター 16px、最小幅 1280px（面接画面）。1280 未満ではプレビューをタブ化して 2 ペインにする。
- タイポ: 本文 14px/1.6、エディタ 14px（設定で 12–18）、日本語は `Noto Sans JP`／等幅は `JetBrains Mono` 相当（要確認: ライセンス同梱可否）。
- 余白 8px グリッド。ペイン境界はドラッグ可、比率は保存。

### 7.2 ダーク / ライト

- OS 設定追従＋手動切替。エディタテーマも連動（Monaco `vs` / `vs-dark` をベースに調整）。
- セッション中はテーマ切替を無効化（画面収録の見た目が途中で変わるため）。
- 録画の視認性のため、ダークでもコントラスト比 4.5:1 以上を UI 文字で保証。

### 7.3 アクセシビリティ

- Monaco のアクセシビリティモード（`accessibilitySupport: on`）を設定から有効化可能。Monaco は Alt+F1 でアクセシビリティヘルプを提供する（要確認: 最新版でのキー）。
- すべてのペインに `role`/`aria-label`、フォーカス順は 問題→エディタ→プレビュー→終了。
- タイマーの色変化には必ずテキスト（残り分）を併記。音通知は ON/OFF。
- 文字起こしは聴覚障害のあるユーザーには役立つ一方、既定 1 行の制約がある。設定で「全文表示」を選べるようにする（原則 2 とのトレードオフを明記）。

### 7.4 アンチ機能（作らないもの）

| 作らない | 理由 |
|---|---|
| セッション中のリアルタイム採点・ヒント表示 | 本番にない。説明が「採点を見ながら」になる |
| AI コード補完（Copilot 等） | 本番再現性。説明力より補完頼みになる |
| 文字起こしの手動修正 UI（セッション中） | 気が散る。終了後にのみ許可 |
| カメラセルフビューの常時表示 | 顔を見続けると説明が止まる |
| 問題をホームで全文プレビュー | 初見力の練習にならない |
| ゲーミフィケーション（連続日数・バッジ・ランキング） | 1 人用ローカルアプリで比較対象がなく、焦りだけ増える |
| 100 点満点の単一スコア | 4 軸＋talking_points 達成の方が行動に繋がる。単一スコアは履歴の要約にだけ使う |
| LLM によるリアルタイム面接官（会話） | 遅延・エコー・品質の不確実性。v1 はテキスト固定台詞 |
| 7 言語全対応を謳うメタデータ | 参照解が無い言語での「対応」は嘘になる |

## 10. v1 スコープ提案

### 10.1 v1 に含める

- 問題: **Core 100 問**（FE 25 / ALG 20 / BE 15 / SEC 15 / SQL 10 / DBG 8 / DATA 5 / SYS 2）＋ generated のうち G1–G6 全通過分（目標 150、保証しない）。fe-0001（Pixiv）を必ず含む。
- 言語: 参照解の優先順位は TS/JS → Python → Go → PHP → Rust → C。v1 で全問題に揃えるのは TS/JS と Python のみ。
- 画面: S0, S1, S2, S3（silent モード）, S4, S5, S6（最小: 一覧＋4 軸推移）, S7（最小）。
- MUST 要件すべて。SHOULD は FR-P-08, FR-P-13, FR-U-12, FR-U-19, FR-U-27 を優先。

### 10.2 v1 に含めない（v2 候補）

- TTS 面接官、LLM リアルタイム面接官、ショートカットカスタマイズ、二言語本文、自動昇格・降格、ヒートマップの詳細、問題タイトル抽象化。

### 10.3 v1 受け入れ基準（抜粋）

1. fe-0001 を 20 分 silent モードで 1 回通し、S5 で「tp1–tp5 の達成状況」「AbortController に言及した時刻」「その時のコード範囲」が同期表示される。
2. Core 100 問すべてが CI で参照解テスト通過（TS/JS, Python）。
3. generated 問題のサンプル 20 問を人が読み、「面接で出題できる」と判定されるのが 15 問以上（75%）。これを下回る場合、generated を v1 から外す。
4. セッション中にユーザーの視線を奪う要素（アニメーション・通知）がゼロであることをレビューで確認。

### 10.4 次に決めるべきこと

- M3 試験形式の一次情報入手（要確認）。入手までは DATA カテゴリの種を凍結。
- 文字起こしエンジンがホットワード/プロンプトに対応するか（R4）。
- Claude 評価の入力形式（動画をどこまで渡すか、ログ主体か）は MCP 側の要件書と整合させる。
