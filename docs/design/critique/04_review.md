# S5 レビュー画面（/sessions/[id]）批評と再設計案

対象: `apps/web/src/app/sessions/[id]/page.tsx`、`apps/web/src/components/review/*`、`apps/web/src/app/globals.css`
根拠資料: 03_evaluation.md §2.2 / §5 / §5.1、04_problems_ux.md §6.4 / §7、CLAUDE.md
スクリーンショット: `design/before/review-desktop-{light,dark}.png`（1440×2688 の全画面。評価あり）、`review-fin-desktop-{light,dark}.png`（finalizing 中で評価なし）、`review-mobile-{light,dark}.png`（390×3996）
方法: dataviz skill の手順（形 → 色 → validator → マーク → hover → a11y）に沿って判断した。色は DADS primitive（tokens 2.1.0）から選び、`validate_palette.js` で light/dark の両方を検証した。数値はすべて実行結果。

## 0. 結論（先に）

1. **最大の問題は「同期」が見た目で崩れていること。** 評価パネル（右カラム）は 2688px まで伸びるが、動画・コード・タイムラインは y≈800 で終わる。下の方の指摘をクリックすると、seek 先の動画とコードは画面外にある（review-desktop-light.png の y=800〜2688 で左 2 カラムが空白）。FR-U-13 は実装上は満たしているが、画面を見る限り満たしていない。
2. **読み順が決まっていない。** 最初に読むべき「総評 1 文」と「次にやること」が 3 カラム目の y≈330〜700 にあり、目はまず空の動画枠と 10 行のコードに向かう。
3. **8 軸レーダーは不適切。** 1 系列で、重みが不均等（20%〜10%）で、軸の並び順で面積が変わる。しかもラベルが切れている（「・復帰力 4」「期 3」「トレー」）。真下に同じ 8 値のリストが重複している。**基準線付きの横棒（1〜5 のドットバー）に置き換える。**
4. **状態色が CVD で破綻している。** 現行の danger/warn/ok は、全ペア比較で red↔green の deutan ΔE が 3.3（FAIL）、red↔orange の通常視覚 ΔE が 13.0（FAIL）。ピンは菱形 1 種類で、色しか違わない。
5. **再設計の骨格:** スクロールは 1 枚のまま。上から ①サマリ帯、②1 画面高の「再生ワークスペース」（タイムラインを全幅に置き、下に 動画＋文字起こし／コード／指摘一覧 の 3 列。各列は内部でスクロール）、③軸別詳細、④解説。sticky プレイヤーはモバイル（<1280）だけで採用する。

## 1. 現状の問題点（重大度順）

重大度: **S1** = 目的（振り返り）を阻害 / **S2** = 誤読・アクセシビリティ違反 / **S3** = 品質・一貫性

### S1-1 同期 UI なのに、同期先が画面外に流れる
- 3 カラムのグリッドが `ReviewScreen.tsx:286`（`xl:grid-cols-[minmax(300px,1fr)_minmax(380px,1.4fr)_minmax(340px,1.1fr)]`）。高さを揃える仕組みがなく、評価列だけが長い。review-desktop-light.png では、左・中央の列が y≈800 で終わったあと、約 1900px が空白になっている。
- フィードバック（`EvaluationPanel.tsx:235-278`）・軸の根拠（`:222-227`）・沈黙区間（`MetricsSummary.tsx` の details）をクリックすると seek は起きる。しかし動画（`VideoPane`）とコード（`CodeAtT`）は上にスクロールして消えているので、何が起きたかが見えない。
- モバイル（review-mobile-light.png）はさらに悪い。動画が y≈500、フィードバックが y≈2700 にある。

### S1-2 「何から見ればよいか」の導線がない
- 視線は 左上 → 右へ流れるので、最初に見えるのは 空の動画枠（「動画を読み込めませんでした」）、文字起こし、10 行のコードになる。総評（`EvaluationPanel.tsx:174`）は右列の y≈650。
- 総評が next_practice より**後**にある（`:142-174`）。「なぜその 3 件なのか」の文脈がない状態で行動指示を読むことになる。
- review-fin-desktop-light.png（評価なし）では、右列の先頭がグレーアウトした「Claude で評価する」ボタンで、何を待てばよいかは処理中バナーにしか書かれていない。

### S1-3 情報量が多すぎ、重複している
評価列に 11 ブロックが縦に並ぶ: 評価メタ、次にやること×3、総評、要件チェック、レーダー、軸リスト、フィードバック、模範解答比較、不確実性、話すべきポイント、指標、解説。重複は次のとおり。
- レーダーと軸リストが同じ 8 値を出している（`EvaluationPanel.tsx:208` と `:209-231`）。
- 要件チェック（Claude 判定）と話すべきポイント（機械判定）が同じ論点を別ラベルで出している。例: 「古いリクエストの中断」は要件では **言及のみ**、話すべきポイントでは **あり**。意味は違う（実装か発話か）が、並べると矛盾に見える（review-desktop-light.png y≈640 と y≈1570）。
- 模範解答比較が要件 ID（`no_empty_query`, `abort_stale`）を mono で出していて（`:283-285`）、要件チェックのラベルと対応が取れない。

### S1-4 タイムラインが読めない（レーン・ピン・密度）
`CodeTimeline.tsx` 全体。crops/tl-light.png で確認した。
- **凡例がない。** 菱形（feedback）、▲（run）、点線＋●（followup）、灰帯（沈黙）、青の濃淡（編集密度）の意味がどこにも書かれていない。
- **ピンは菱形 1 種類で、severity を色だけで区別している**（`:180-188`）。番号もないので、右列のどの指摘かを対応付けられない。
- **範囲を持つ指摘（`t_end`）が点で描かれている。** 「01:00–03:20 無発話で実装」が 01:00 の 1 点になる。
- **沈黙帯が全レーンを覆っている**（`:119-123`、opacity 0.08/0.14）。編集ブロックの上にも灰色が重なり、密度の濃淡が背景によって変わってしまう。dark（tl-dark.png）では沈黙帯が**面より明るく**なり、「選択範囲」に見える。
- **密度を opacity で表しているが、最小値が 0.15 で凡例もない**（`density.ts:68`, `CodeTimeline.tsx:144`）。240 バケットの細い縦棒がちらつくだけで、「どの時間帯に集中して書いたか」が読めない。
- **フェーズ推定が別の場所にある。** 同じ時間軸のデータなのに、指標カード下の独立した帯に描かれ（`MetricsSummary.tsx:53-62`）、タイムラインと横位置が合わない。
- 文字が小さい: レーン名は 10px、目盛りは 9px（`:126,138,162`）。モバイルでは目盛り同士が重なる（review-mobile-dark.png y≈218「01:0002:0003:00…」）。

### S2-1 状態色がアクセシブルでなく、意味の衝突もある
- validator（`--pairs all`。ピンは隣接順を選べないので全ペアで見る）の結果、現行の `#c43d3d / #c7730a / #2d8a4e` は **CVD ΔE 3.3（deutan, red↔green）FAIL、通常視覚 ΔE 13.0（red↔orange）FAIL**。major と minor は色覚が典型的な人でも見分けにくい。
- dark に `--warn/--danger/--ok` の再定義がない（`globals.css:15-17` は :root だけ）。危険色の文字は dark 面で 3.27:1。
- 要件チップの文字は 10px で、`text-ok` は 4.32:1、`text-warn` は 3.57:1 になり、小さい文字の AA（4.5:1）を満たさない（`EvaluationPanel.tsx:19-23,195`）。
- **warn 色を「状態」以外にも使っている。** 文字起こしの根拠ハイライト（`TranscriptPane.tsx:94` `bg-warn/10`）、コード行ハイライト（`CodeAtT.tsx:236`）、followup ピン（`CodeTimeline.tsx:202-203`）、フェーズ「整形」（`MetricsSummary.tsx:16-22`）。フェーズ「検証」も ok 色。dataviz の「status は予約色」に反しており、黄色を見ても「要注意」なのか「選択中」なのか判断できない。

### S2-2 レーダーチャートの妥当性（dataviz の判断）
- データの役割は「8 項目の量を共通の尺度（1〜5）で比べる」こと。choosing-a-form の規則では **bar** が既定。レーダーは
  - 面積が軸の並び順と隣の軸の値に依存する。重み（R4 20%、他 10〜15%）が反映されないので、面積が総合点を誤って示唆する。
  - 1〜5 尺度を半径 0〜5 に写しているので、1 点でも面積が出る（`radar.ts` のコメントが自覚している）。
  - 角度方向の比較は長さの比較より不正確。
  - ラベルが切れている: `Radar.tsx:23` の `r = size/2 - 40` で 260px の SVG では左右ラベルが収まらない（crops/radar-light.png の「・復帰力 4」「期 3」「トレー」「実装正確性」の点数欠落）。
  - confidence を中抜きの点（`:45`）でしか表していない。中抜きと塗りの差は 3.5px で、ほぼ見えない。
- **判定: 置き換える。** 用途を「過去回との形の比較」に絞る場合でも、small multiples の横棒の方が読める。

### S2-3 指標カードに意味付けがない
- `MetricsSummary.tsx:42` の 3×2 カードは、数値（mono, `:36`）、10px の補足、比較対象なしで構成されている。「発話比率 38%」が良いのか悪いのかがわからない。「数値は解釈を添えずに出す」（`:3-6`）方針は理解できるが、**ルーブリックが持つ閾値（R7: silent_edit_ratio < 0.2、R8: 沈黙 >15s など）は解釈ではなく定義**なので、基準線として出してよい。
- 指標がどの軸の根拠なのか（R5 ← 実行回数、R7 ← 説明先行・無発話編集、R8 ← 沈黙）がつながっていない。軸リストの根拠ボタン（`metric silence_gt15s[2]`）から指標カードへは移動できない。

### S2-4 ピンと本文の対応が取れない
- next_practice のチップは `f1 00:26` と表示されている（`EvaluationPanel.tsx:157-159`）が、フィードバック一覧には ID が出ていない（`:243-256`）。タイムラインのピンにも番号がない。「f1 はどれか」を 3 か所で照合できない。
- 指摘の詳細は選択時にしか展開されない（`:257`）。ピンをクリックすると右列の該当項目が開くが、その位置へはスクロールしない（画面外のまま）。

### S2-5 キーボードとスクリーンリーダー
- タイムライン SVG は `role="slider"` なのに `tabIndex` もキー操作もない（`CodeTimeline.tsx:103-117`）。フォーカスできない slider になっている。
- ピンは `<g onClick>` で、フォーカスもできず、名前も持たない（`:184,194,201`）。`<title>` はツールチップとしてしか機能しない。
- レーダーの軸ラベルは `<text onClick>`（`Radar.tsx:65`）で、キーボードから選べない。
- グローバルの keydown で Space を preventDefault している（`ReviewScreen.tsx:204-209`）。除外対象に BUTTON が入っていないので、**フォーカス中のボタンを Space で押せない**（再生が切り替わる）。WCAG 2.1.1 上の問題。
- 重大度ドットは `aria-hidden` で、重大度は英語の `major` を 10px で出しているだけ（`EvaluationPanel.tsx:244,252`）。
- フォーカスリングはブラウザ既定のまま。DADS の「黒 4px アウトライン＋黄リング」に相当するものがない。

### S2-6 モバイル（<1280）
- 縦に全部積んでいて 3996px ある。04 §7.1 の「1280 未満はタブ化」を満たしていない。
- 自前のトランスポートと `<video controls>`（`VideoPane.tsx:119`）が二重にある（review-mobile-dark.png y≈115 と y≈400）。
- ピンの当たり判定は半径 5px（`CodeTimeline.tsx:182`）。dataviz の 24px にも DADS のタップ目標 44px にも届かない。

### S3-1 ダークモード
- 沈黙帯が面より明るく見える（S1-4）。フェーズ「停滞」の色が `--border`（#2c2c2f）で、凡例のチップが見えない（crops/lower-dark.png）。
- 再生ヘッドのラベル（`fill=var(--fg)`、`:211`）が白い塊になり、light より目立つ。

### S3-2 その他
- `EvaluationPanel.tsx:14` のコメント「総合点は小さく（FR-E-09）」は参照違い。FR-E-09 はローカル保存の要件。
- ルーブリックの重みがドキュメントと実装で食い違っている: 03 §2.2 は R3=15%・R8=5%、`packages/core/src/evaluation.ts:25,30` は R3=10%・R8=10%。UI に重みを表示する前に、どちらが正しいかを決める必要がある（本稿の範囲外。指摘のみ）。
- 処理中バナー（`ReviewScreen.tsx:239-244`）が「●＋1 行」の独自実装で、警告と情報の区別がない。

## 2. 再設計: 読み順とレイアウト

### 2.1 読み順（ユーザーの問いの順）
| 順 | 問い | ブロック | 主要データ |
|---|---|---|---|
| 1 | 結局どうだった？ | **サマリ** | summary 1 文、総合点（小さく）、評価メタ（Dl, 折りたたみ） |
| 2 | 次に何をする？ | **次の練習 3 件** | next_practice（根拠ピン番号つき） |
| 3 | 要件は満たした？ | **要件チェック** | requirement_checklist（3 状態チップ＋時刻リンク） |
| 4 | どこで何が起きた？ | **タイムライン付き再生** | タイムライン、動画、文字起こし、コード、指摘一覧 |
| 5 | 軸ごとの根拠は？ | **軸別詳細** | 8 軸ドットバー、rationale、evidence、関連指標（基準線つき）、話すべきポイント |
| 6 | 正解は？ | **解説** | 振り返り解説、参照解、隠しテスト（Disclosure、既定で閉じる） |

### 2.2 レイアウト方式の比較（批判的に選ぶ）
| 案 | 長所 | 短所 | 判定 |
|---|---|---|---|
| A. 全面タブ（概要/再生/軸/解説） | 1 画面の情報量が減る | 同期が**タブをまたぐ**。概要の指摘をクリックすると再生タブに飛ぶので、「指摘本文と動画を並べて見る」ことができない。FR-U-13 の価値が消える | 不採用（≥1280） |
| B. 1 枚スクロール＋sticky プレイヤー | どこからでも seek 結果が見える | 動画＋タイムラインを sticky にすると、1440×900 の 45% 前後を常に占有する。軸別詳細を読むときに残るのが細い帯だけになる | ≥1280 は不採用。**<1280 で採用** |
| C. 1 枚スクロール＋**1 画面高のワークスペース** | サマリは普通の文書として読める。ワークスペース内では 再生・コード・指摘 が常に同じ画面にある（各列が内部でスクロール） | 内部スクロールが入れ子になる。ホイールが閉じ込められないように、列の端まで行ったらページスクロールに抜ける既定挙動を維持する | **採用（≥1280）** |

C の補足:
- サマリ帯の「次の練習」「要件チェック」のリンクを押すと、ワークスペースを `scrollIntoView({block:"start"})` で画面に入れてから seek する。同期先が必ず見える。
- ワークスペースの高さは `calc(100dvh - 56px)`、最小 640px。タイムラインはワークスペースの最上段に全幅で置き、ワークスペースの中では動かない（sticky 不要）。
- 指摘一覧はワークスペース右列に置く。ピンと同じ番号・同じ形で並べ、これをタイムラインの**表ビュー**としても使う（dataviz の「table view twin」）。

### 2.3 総合点の扱い
dataviz の「hero figure（≥48px）」はこの画面では**使わない**。03 §2.2 と 04 §7.4 は総合点を目立たせない方針なので、ヒーロー位置には総評の 1 文を置き、総合点は 14px の補助テキスト「総合 3.4 / 5（重み付き平均）」にとどめる。

## 3. タイムライン視覚仕様

### 3.1 レーン構成（上 → 下、px は ≥1280 の場合）
| レーン | 高さ | 形式 | 色の役割 |
|---|---|---|---|
| 目盛り＋再生ヘッドの時刻 | 20 | 上端に時刻ラベル（12px, tabular-nums）。再生ヘッドのラベルは**上に**置き、目盛りと重ねない | 文字は text token |
| 指摘ピン | 28 | 形＋番号（§3.2）。`t_end` がある指摘は 2px の範囲バーも引く | **status** |
| 面接官 | 16 | 吹き出し「?」アイコン（12px）。followup のみ | 中立（gray-600 / gray-400） |
| フェーズ | 16 | 区間ごとの矩形。**中に文字**（設計/実装/検証/整形/停滞）。入らない幅ならツールチップに逃がす | **色を使わない**: gray-50/100 を交互に塗り、2px の面ギャップで区切る。「停滞」だけ gray-200 |
| 発話 | 14 | 発話区間を gray-500 のバーで表す。**沈黙（15 秒超）**はこのレーンの中だけに中抜きの枠＋文字「沈黙 140s」で示す（全レーンには広げない） | 中立 |
| ファイル（1 本 / ファイル） | 16 | 編集量を **4 段の ordinal**（log 量子化）で塗る。バケットは 240 → 「6px 以上」になる数に動的調整 | **ordinal 1 色相（DADS blue）** |
| 実行 | 16 | ✓（AC/PASS）と ✕（それ以外）のアイコン＋入る幅なら「AC」の文字 | **status** |
| 要件（ゴースト） | 0 | 要件チェックの行に hover/focus したときだけ、`mentioned_at`（吹き出し）と `code_ref.at`（コード記号）を 40% の不透明度で表示する | status（淡色） |

- 罫線は 1px の実線で、面から 1 段だけ離れた灰色（light `#e6e6e6` = solid-gray-100 / dark `#2c2c2f`）を使う。破線は使わない（現行 followup の破線 `:202` は廃止する）。
- 選択中の指摘は、`t..t_end` の範囲を全レーンにわたって status 色 10% の wash で塗る（未選択時は塗らない）。

### 3.2 重大度・状態の符号化（色＋形＋文字の三重化）
| 意味 | 対象 | 形（12〜14px） | 文字 | light（面 #fff） | dark（面 #1d1d1f） |
|---|---|---|---|---|---|
| 重大 / なし / 失敗 | feedback major, requirement missing, run WA | ▲（上向き三角）/ ✕ | 「重大」「なし」「WA」 | red-900 `#ce0000`（5.79:1） | red-600 `#fe3939`（4.70:1） |
| 改善 / 言及のみ | feedback minor, mentioned_only | ◆（菱形） | 「改善」「言及のみ」 | yellow-700 `#b78f00`（3.02:1） | yellow-600 `#d2a400`（7.25:1） |
| 良い / 実装あり / 成功 | feedback positive, implemented, run AC | ●＋白抜き ✓ | 「良い」「実装あり」「AC」 | cyan-700 `#008da6`（3.92:1） | cyan-600 `#00a3bf`（5.60:1） |

**validator の結果（`--pairs all`。ピンは任意の 2 つが隣り合うため全ペアで検証）**
- light（#ffffff）: Lightness PASS / Chroma PASS / **CVD ΔE 12.6（deutan, yellow↔red）PASS** / 通常視覚 ΔE 23.0 PASS / コントラスト 全色 ≥3:1 PASS。ページ地 #f7f7f5 上では yellow が 2.82:1（WARN）なので、マークは必ず形と文字を伴わせる（relief）。
- dark（#1d1d1f）: **CVD ΔE 8.5 PASS** / 通常視覚 ΔE 22.6 PASS / コントラスト PASS / Lightness は yellow のみ L=0.74 で帯外（FAIL）。帯の規則は categorical 系列の調和のためのもので、status の warning が明るい黄であることは参照パレットでも同じ。**意図的な逸脱として記録する。**
- 比較: 現行の `#c43d3d/#c7730a/#2d8a4e` は CVD 3.3 / 通常視覚 13.0 の両方で FAIL。DADS の semantic（success=green-600 系）をそのまま使う案 B（`#ce0000/#b78f00/#1d8b56`、dark は `#fe3939/#d2a400/#2cac6e`）は CVD 7.4（WARN、二次符号化が必須）になる。形と文字を必ず付けるので案 B も合法だが、**A（cyan）を推奨**する。「良い」が青緑に見える違和感は、✓ アイコンと「良い」の文字で吸収できる。
- 文字に status 色を使わない。チップは DADS ChipLabel の filled-1 の構造（枠＝濃い段、地＝50 段、文字＝1000〜1100 段）に合わせる。light では red-1000 on red-50 が 6.94:1、yellow-1100 on yellow-50 が 6.43:1、cyan-1000 on cyan-50 が 6.47:1。dark では地を「status 色 16% ＋ 面」、文字を `--fg`、枠を上表の dark 色にする（DADS は dark を持たないため自前で定義。§5）。

### 3.3 編集量（ordinal）
- light: blue-400 `#7096f8` → blue-600 `#3460fb` → blue-800 `#0031d8` → blue-1000 `#00118f`。validator `--ordinal`: 単調 PASS / 隣接 ΔL ≥0.06 PASS / 最淡段 2.84:1 PASS / 色相差 3°。
- dark: blue-700 `#264af4` → blue-500 `#4979f5` → blue-400 `#7096f8` → blue-200 `#c5d7fb`（多いほど明るい）。最暗段 2.70:1 PASS。
- 不透明度による濃淡はやめる。下地（沈黙帯など）で色が変わり、凡例で示せないため。
- 凡例は「編集量 少 ▮▮▮▮ 多」の 4 マス。値は「1 バケットあたりの変更文字数」で、各段の境界をツールチップに出す。

### 3.4 hover / focus の詳細（ツールチップ）
- 値を先に、ラベルを後に書く（dataviz interaction）。例:
  ```
  ② 01:00–03:20 （2 分 20 秒）
  ◆ 改善 · 説明と実装の同期
  無発話でキャッシュを実装
  Enter で選択 · 根拠 1 件
  ```
- ファイルバケット: 「index.html 04:10–04:12 · 3 編集 / 58 文字」。沈黙: 「沈黙 140 秒 · 編集あり · 01:00–03:20」。
- 当たり判定は 24×28px 以上（マークが 12px でも）。ピン同士が 24px 未満に近づいたら「+2」のクラスタにまとめ、クリックで拡大表示する。
- ツールチップは補助にとどめる。同じ情報は右列の指摘一覧（表ビュー）で読めるようにする。キーボードフォーカスでも hover と同じ内容を出す。
- ラベルは `textContent` で入れる（文字起こしの引用は未信頼データとして扱う）。

### 3.5 キーボード
- スクラブ領域は `role="slider"` + `tabIndex=0`。←/→ で ±5 秒、Shift+←/→ で ±1 秒、Home/End で端へ移動する。`aria-valuetext="03:20 / 10:00"`。
- ピン列は `role="toolbar"` + roving tabindex（ピン列全体で Tab 1 回）。←/→ で前後のピン、Enter で選択。各ピンの名前は「② 改善 01:00 無発話でキャッシュを実装」。
- グローバルショートカット（Space, j/k）は、`button, a, summary, [role=tab], [role=slider]` にフォーカスがあるときは発火させない（S2-5 の修正）。

### 3.6 凡例（常設）
タイムラインの上に 1 行で置く（DADS の小さい本文 14px、文字は text token、記号だけ色付き）:
`▲ 重大  ◆ 改善  ● 良い  ? 面接官  ✓/✕ 実行  ▭ 沈黙15秒超  編集量 ▮▮▮▮  ［表で見る］`
「表で見る」は DADS Table のモーダルを開き、全イベント（時刻・種別・内容・リンク）を表で見せる。

## 5. DADS を当てはめるべきでない箇所

1. **ダークモード全般。** DADS の React 実装は `bg-white` / `text-solid-gray-800` を直書きしていて（例: Tab `TabItem` の `bg-white`、ChipLabel outlined の `bg-white`）、dark のトークンがない。04 §7.2 は dark を必須にしているので、**DADS のクラスをそのまま持ち込まない**。トークン（色の段）だけ借りて、`--status-*` / `--viz-*` を :root と dark の両方で定義する。
2. **タイムライン・ドットバーなどのチャート描画。** DADS にはデータ可視化の部品も規則もない。マーク仕様（2px 線、8px 以上のマーカー、面ギャップ、凡例、ツールチップ、表ビュー）は dataviz の手法に従い、DADS からは色の段だけを取る。
3. **semantic 色の流用。** DADS の success/error/warning（green-600 / red-800 / yellow-700）を全ペアで見ると、CVD は 7.4（WARN）でぎりぎり。ピンのような小さいマークを密に並べる用途にはそのまま使わない（§3.2 の案 A）。
4. **本文 16px・行間 1.7 と 44px のタップ目標を全要素に適用すること。** ワークスペースは情報密度が要る道具 UI（エディタ・タイムライン・文字起こし）。≥1280 では本文 14px（04 §7.1 の規定）、タイムラインのラベル 12px、行の最小高さ 32px にし、DADS の 16px は総評・次の練習・軸別詳細の読み物部分だけに使う。モバイルの sticky プレイヤーのピンは 44px を守る。
5. **Tab をデスクトップの再生エリアに使うこと。** §2.2 A のとおり、同期を壊す。DADS の Tab 自体は正しい部品だが、使う場所を間違えない。
6. **Monaco（コード）と動画の中身。** Monaco のテーマ（`vs`/`vs-dark`）とシンタックス色は DADS の色に寄せない。コードの読みやすさが優先で、ハイライト行の色だけを `--hl-line`（中立の黄ではなく accent 10%）に変える。動画は黒背景のままにする。
7. **Heading の大きなスケール。** h1 に DADS の 32px 以上を使うと、ワークスペースが画面に収まらない。h1 は 20px、セクション見出しは 16px bold で十分。
8. **ゲーミフィケーション的な「ステップ」表現。** StepNavigation / ProgressIndicator で「評価の進み具合」を飾らない（04 §7.4 のアンチ機能に近い）。処理中は NotificationBanner の 1 行だけにする。
